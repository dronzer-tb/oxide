What is a chunk?

Minecraft doesn't build the world all at once. It builds it in chunks — vertical columns 16 blocks wide, 16 blocks deep, and 384 blocks tall, running from bedrock at Y −64 up to build limit at Y 320.

That's 98,304 blocks in a single chunk. Every one of them has to be decided: stone or air, water or lava, grass or sand. Then caves get carved through it, ore gets injected, trees get planted, and structures get stamped in.

Think of it like

A chunk is one tile of an enormous mosaic. The world is infinite, so the game only makes tiles when someone walks toward them. Every tile needs ~98,000 individual decisions, and the game has to finish before you arrive — or you fall through the floor.

CPS, DPS and MSPT

Three numbers get thrown around constantly. Here's what each one measures.

CPS — Chunks Per Second
How many chunks finish generating every second. Vanilla manages around 22. Oxide holds 810. This is the headline number: higher means the world builds faster and you stop hitting invisible walls.
DPS — Data Per Second
How much finished chunk data actually leaves the server and reaches players. Generating fast doesn't help if the data can't get out — this is the number Pacside exists to raise.
MSPT — Milliseconds Per Tick
Minecraft updates the world 20 times per second, so each update ("tick") has a 50 ms budget. MSPT is how much of that budget got used. Go over 50 and the server drops below 20 TPS — that's lag. Oxide's generation costs 0.83 ms, leaving 98% of the budget for everything else.
How they connect

High CPS with high MSPT is worthless — you generated fast but froze the server doing it. The real goal is high CPS at low MSPT: build the world quickly while barely touching the tick budget. That's the entire design target.

Why vanilla is slow

Minecraft's server runs on Java. Java allocates objects on a shared heap and a background process — the garbage collector — periodically sweeps up whatever's no longer used.

Worldgen creates an enormous amount of short-lived garbage. Every block placement, every noise sample, every biome lookup allocates. Generate a few thousand chunks and the collector has to stop the world to clean up. The server tick stalls. CPS collapses.

Vanilla

Millions of small objects per second. Garbage collector pauses at unpredictable moments. Worldgen competes with mob AI, redstone and player packets for the same 50 ms budget.

Oxide

No allocations in the hot path. Terrain is computed into pre-sized native buffers and written once. Nothing to collect, so nothing to stall on.

What Oxide does

Oxide is a full reimplementation of Minecraft's world generator in Rust — a language with no garbage collector, direct memory control, and access to your CPU's vector instructions.

It does everything the vanilla generator does: evaluates the noise graph that shapes terrain, resolves biomes from six climate axes, applies surface rules that decide grass versus sand versus terracotta, floods aquifers, carves caves, injects ore veins, picks structure locations and assembles Jigsaw buildings piece by piece.

The important part: it's compatible

Oxide isn't a different world generator that happens to be fast. It reads your existing datapacks — Terralith, Incendium, Yggdrasil, all 150 of them — and reproduces vanilla's exact math, down to matching Java's random number generator bit for bit. Same seed, same world, 37 times faster.

Think of it like

Same recipe, same ingredients, same result — but the kitchen was rebuilt around the cook instead of the other way around.

What Pacside does

Once Oxide made generation fast, a second bottleneck showed up immediately: getting the chunks to the player.

Normally the server reads a chunk off disk, converts it to a network packet, compresses it, and sends it — every single time anyone needs it. Flying on an Elytra at 35 m/s, you cross a chunk boundary roughly three times per second in every direction at once. The server can't keep up, so you rubber-band, or the world just stops loading.

Two ideas

Off-heap caching. Pacside compresses each chunk packet once and keeps it in native memory — outside the Java heap, so the garbage collector never touches it. 32,000 chunks live in about a gigabyte of RAM, sharded across 32 lanes so threads never wait on each other. A repeat request is a memory read, not a disk read.

Predictive prefetch. Instead of waiting for the client to ask, Pacside watches your velocity vector and projects a cone 16 chunks ahead along your heading, fanning out five ways so turns are covered too. By the time you arrive, the terrain is already compressed and waiting.

Staying smooth

Prefetching thousands of chunks at once would flood the scheduler and tank TPS. Pacside paces itself with a token bucket — 24 chunks per tick, about 480 per second — which keeps region tick time under 3 ms and TPS pinned at 20.0.

Think of it like

A road crew that watches which way your car is pointed and finishes the asphalt just before you get there — instead of a crew that starts digging when you honk.

What Vertex Engine does

Oxide as a normal plugin has to be polite. Bukkit — the plugin API — gives it a sandboxed wrapper object to fill in, then copies that into the real chunk afterward. Every block goes through a conversion layer.

Vertex Engine is a fork of the server that removes the wall. It exposes a small interface where a native module can be handed a raw pointer to the actual memory a chunk section lives in. Oxide writes terrain straight into the server's own data structures — no wrapper objects, no BlockState conversion, no copy.

Plugin mode — 810 CPS

Rust generates into a buffer, Panama copies it across, Bukkit wraps it, the server copies it again into the real chunk. Two copies and a conversion per chunk.

Vertex mode — 1,550 CPS

Rust receives the address of the real chunk section and writes into it directly. Zero copies. Multiple sections written concurrently across cores.

It's also generic — Vertex is a module system, not an Oxide-specific hack. Any native engine can plug into the same interface.

What the FFI is

FFI stands for Foreign Function Interface — the bridge that lets code written in one language call code written in another. Here it's Java calling Rust.

The old way (JNI) was slow and awkward: every call crossed a wrapper layer, and data had to be copied into a shape the other side understood. Java 22 introduced Panama, which lets Java call native functions almost as cheaply as its own methods, and share memory regions directly instead of copying them.

Think of it like

JNI was mailing photocopies back and forth. Panama is both people working on the same sheet of paper on the same desk.

This is what makes the whole architecture viable. Without cheap calls and shared memory, the cost of crossing between Java and Rust would eat the speedup Rust provides.

Why Rust specifically

Three reasons, in order of how much they matter here.

1. No garbage collector

Rust frees memory the moment it goes out of scope — decided at compile time, not by a background process. There are no collection pauses because there is no collector. For a workload that allocates constantly, this alone is most of the win.

2. Real control over memory layout

Rust lets you decide exactly how data sits in memory. Pack chunk data so a whole section fits in CPU cache and the processor stops waiting on RAM — which is where most of the remaining time goes.

3. Safety without a runtime

C could do the first two, but a mistake in C corrupts memory silently and crashes the server hours later. Rust's compiler rejects those mistakes before the code runs, with no runtime checks to pay for.

Why any of this matters

On a normal server, exploring new territory is where everything falls apart. Chunks arrive late, TPS drops, players rubber-band, and the admin's answer is usually "pre-generate the world overnight and hope nobody goes further."

With this stack, generating a 10,000 × 10,000 block world takes nine minutes instead of five and a half hours. New terrain appears as fast as you can fly toward it. The server barely notices — 0.83 ms out of a 50 ms budget.

And none of it changes the world you get. Same seed, same datapacks, same terrain, same structures. Just without the wait.
